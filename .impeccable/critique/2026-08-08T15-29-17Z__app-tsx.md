## Overall Impression

Media Scribe looks polished enough to signal a capable technical tool, and its state handling is stronger than its first impression suggests. The problem is sequencing: the page asks users to assemble infrastructure before it lets them feel the simple promise—choose media, transcribe it, use the result. The single biggest opportunity is an upload-first job composer with a compact processing/privacy summary and advanced configuration moved behind progressive disclosure.

## Cognitive Load

The interface fails 7 of 8 checklist items, producing **high cognitive load**. Grouping passes because controls are sectioned and carded; single focus, chunking, visual hierarchy, one-thing-at-a-time, minimal choices, working memory, and progressive disclosure fail.

Decision points exceeding four visible options include 10 LLM preset models, 5 STT engines, 10 language choices when opened, 8 STT presets, and potentially unbounded discovered-model chips. The overload is not inherent to transcription; it comes from exposing implementation choices before user intent has been established.

## Emotional Journey

The header opens with capability and privacy. The first emotional valley arrives immediately when a large, expanded server-configuration wall replaces that promise with infrastructure anxiety. Processing feedback restores reassurance, but the lack of cancel or ETA—and a synthetic progress animation that rises to 95%—can erode trust. Completion peaks briefly with a readable result and clear Copy confirmation, then ends weakly because there is no editing, download/export, output metadata, or explicit next-job path.

## What’s Working

- Conditional provider and pipeline sections prevent every configuration from appearing simultaneously, while saved settings reduce repeat setup.
- File preview, filename, and size confirm that the intended media was selected before processing.
- Upload/processing messages, model-discovery feedback, and the labeled “Copied” state provide useful, immediate confirmation.

## Priority Issues

### 1. [P1] The core task is buried beneath setup

**Why it matters:** The expanded settings panel precedes upload and consumes most of the page. New users can reasonably conclude that configuring local infrastructure is mandatory before they can transcribe anything.

**Fix:** Lead with media selection. Show one compact row for processing route, privacy/location, and language; collapse endpoints, credentials, and model identifiers into Advanced settings. Remember advanced choices without keeping them open.

**Suggested command:** `$impeccable distill`

### 2. [P1] The upload paths exclude keyboard and screen-reader users

**Why it matters:** Both upload areas are clickable `<div>` elements driving hidden inputs, without native button/label semantics, keyboard activation, or a clear accessible name. Async status changes also lack live announcements.

**Fix:** Use styled `<label>` or button semantics, visible focus, Enter/Space activation, accessible descriptions, and `aria-live` regions for upload, processing, success, and error states. Verify at 200% zoom.

**Suggested command:** `$impeccable audit`

### 3. [P1] Choice overload replaces guidance

**Why it matters:** Users choose engines, modes, endpoints, credentials, languages, and many model chips without a recommended route or compatibility filtering. This forces novices to learn the architecture and still slows experts.

**Fix:** Introduce Basic and Advanced modes. Auto-detect available services, recommend a compatible pipeline, keep one default visible, and convert large chip collections into searchable controls filtered by engine.

**Suggested command:** `$impeccable shape`

### 4. [P1] Guardrails and recovery are incomplete

**Why it matters:** Picker validation differs from drag-and-drop validation; users can construct incompatible configurations; failures rely on alerts or raw errors; processing lacks cancel and direct retry.

**Fix:** Centralize file validation, expose accepted formats and limits before selection, add endpoint connection tests and compatibility checks, preserve user work, and offer actionable inline Cancel, Retry, and Change settings controls.

**Suggested command:** `$impeccable harden`

### 5. [P2] Completion is a dead end

**Why it matters:** The finished transcript supports Copy only. Users cannot correct text, download a useful format, inspect metadata, or deliberately begin another job.

**Fix:** Add an editable review state, TXT/Markdown/SRT or other validated export formats, media/language/processing metadata, and a clear “Transcribe another file” action.

**Suggested command:** `$impeccable shape`

## Persona Red Flags

**Alex (Power User):** There are no keyboard shortcuts, batch uploads, recent jobs, export formats, or quick rerun. Alex must repeatedly traverse an oversized setup surface for a one-file workflow and cannot cancel a mistaken job.

**Jordan (First-Timer):** Before the obvious first action, Jordan encounters “Translation & Processing Engine,” CORS, STT, vLLM, ports, bearer tokens, and model IDs. There is no recommended route or task-focused help, so abandonment is likely before upload.

**Sam (Accessibility-Dependent):** Sam cannot keyboard-activate either custom dropzone, does not receive live announcements for important state changes, and encounters selected states communicated partly through color and pulsing dots. Frequent 9–10px muted text also creates low-vision friction.

## Minor Observations

- “100% offline ready” sits beside Gemini, Groq, and hybrid cloud routes without a persistent, near-action explanation of where the selected file will be processed.
- The document title says “WebM Scribe” while the product header says “Media Scribe”; “translation” is used where the task is transcription.
- Pulsing selection indicators lack an evident reduced-motion treatment.
- The detector’s Inter and gradient-text findings are not severe alone, but together they explain why the interface feels like a stock AI dashboard rather than a transcription workspace.

## Questions to Consider

- Should infrastructure setup be a prerequisite, or a secondary drawer after media selection?
- If privacy is the promise, can “where this file will be sent” appear immediately beside Start Transcription?
- Is success raw text copied to a clipboard, or an editable, exportable working transcript?
- Could backend detection recommend a compatible pipeline instead of asking users to assemble one?
